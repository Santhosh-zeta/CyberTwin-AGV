TwinWare: Project Execution & Team Work Plan

1. PROJECT AT A GLANCE

Project Name: TwinWare Full Title: Design and Implementation of an Edge-Based Cyber-Physical Digital Twin Framework for Autonomous Warehouse AGVs using Raspberry Pi 5 and ESP32

What we are building: A miniature autonomous warehouse system where a physical Automated Guided Vehicle (AGV) is mirrored by a live Digital Twin. The system uses an ESP32 for real-time motor and sensor control, and a Raspberry Pi 5 as an edge node to process telemetry, host the backend, and maintain the Digital Twin state.

Why we are building it: To demonstrate edge-based computation and cyber-physical systems (CPS) in a practical, physical format, bridging the gap between low-level embedded hardware and high-level digital orchestration.

Main Technologies: * Hardware: ESP32, Raspberry Pi 5, DC Motors with Encoders, Sensors. * Communication: UART, MQTT. * Software Stack: C/C++ (ESP32), Python/FastAPI (Edge), SQLite, web-based dashboard (HTML/JS/CSS).

Final Demonstration: The AGV will complete a warehouse mission while dodging an obstacle. A web dashboard will simultaneously display the exact digital twin counterpart mirroring the AGV’s movements and state in real-time.

Core Team: Two students: * Member A (Embedded & Robotics Lead) * Member B (Edge, Digital Twin & Software Lead)

Expected Final Outcome: A fully functional, synchronized physical-to-digital system capable of executing commands and displaying low-latency telemetry.

2. WHAT EXACTLY ARE WE BUILDING?

We are building a closed-loop Cyber-Physical System where a physical robot is continuously synchronized with a virtual model.

The Complete Flow:

Physical AGV
      ↓
Sensors + Motors
      ↓
ESP32
      ↓
UART
      ↓
Raspberry Pi 5
      ↓
MQTT + Backend + Database
      ↓
Digital Twin
      ↓
Web Dashboard
      ↓
Commands
      ↓
Raspberry Pi
      ↓
ESP32
      ↓
Physical AGV

The Digital Twin is NOT merely a dashboard. It is the central digital representation of the current state of the physical AGV and its environment. When the physical AGV moves, the twin moves. When a command is issued to the twin, it is translated and executed by the physical AGV.

4. SYSTEM ARCHITECTURE

Physical Layer

  • Chassis & Locomotion: Acrylic/3D printed chassis, DC geared motors, Wheels, Caster.
  • Sensors: Wheel encoders (for odometry), IMU (for heading), Distance sensors (ultrasonic/ToF for obstacles).
  • Power: Li-Po battery pack, Buck converters for Pi and ESP32.

Embedded Layer (ESP32)

Responsibilities: * Direct motor control via motor driver * PWM generation * Encoder reading via interrupts * Sensor reading (IMU, distance) * PID control for straight-line movement * Safety stop logic * UART communication with the edge node * Command execution

Edge Layer (Raspberry Pi 5)

Responsibilities: * UART communication (serial read/write) * MQTT Broker/Client * Telemetry processing and aggregation * Database hosting (SQLite) * Maintaining the core Digital Twin state * High-level navigation computation (waypoints) * Hosting the Backend API (FastAPI)

Digital Twin

Responsibilities: * Maintaining the virtual warehouse state * Syncing physical to virtual AGV * Providing live state data * Logging historical information * Flagging alerts

Dashboard

Responsibilities: * Live 2D monitoring interface * Mission creation and dispatch * Robot status visualization * Analytics and Diagnostics

24. COMMON FAILURE SCENARIOS

Problem: AGV does not move * Check: Battery charge, motor driver power, PWM output from ESP32, physical wiring.

Problem: Encoder readings incorrect * Check: GPIO pin assignment, interrupt setup, encoder wiring, CPR configuration.

Problem: Raspberry Pi doesn’t receive telemetry * Check: UART TX/RX swapped, baud rate mismatch, serial device permissions (/dev/ttyS0), ESP32 actually sending data.

Problem: MQTT doesn’t update * Check: Mosquitto broker running, correct topic, subscriber connected, network issues.

Problem: Digital Twin is out of sync * Check: Timestamp discrepancies, MQTT delays, telemetry processor lag, state update logic in backend.

Phase 2: Raspberry Pi Deployment

Goal: Move the completed, tested software onto the physical hardware.

Once Phase 1 is fully tested, follow these exact steps to deploy to the Raspberry Pi:

Step 1: Prepare the Pi

  1. Flash Ubuntu Server OS onto the Raspberry Pi’s SD card.

  2. Connect the Pi to your Wi-Fi network.

  3. From your laptop, SSH into the Pi:

    ssh username@<raspberry-pi-ip>

  4. Install Docker on the Pi:

    curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker $USER

    (Log out and log back in for docker permissions to apply).

Step 2: Transfer the Code

You can use scp (Secure Copy) to send the required folders from your laptop to the Pi, or push everything to GitHub and clone it on the Pi.

Using scp from your laptop terminal:

scp -r "c:\Users\santh\OneDrive - vit.ac.in\Desktop\XXX\CyberTwin-AGV\raspberry-pi" username@<raspberry-pi-ip>:~/
scp -r "c:\Users\santh\OneDrive - vit.ac.in\Desktop\XXX\CyberTwin-AGV\dashboard" username@<raspberry-pi-ip>:~/

Step 3: Connect Hardware & Run

  1. SSH into the Pi again.

  2. Plug the ESP32 into the Pi via USB.

  3. Check what port the ESP32 was assigned:

    ls /dev/ttyUSB*

    (If it says /dev/ttyACM0 instead, update the SERIAL_PORT variable inside your docker-compose.yml file).

  4. Navigate into the folder:

    cd ~/raspberry-pi

  5. Start the edge servers:

    docker compose up -d --build

  6. Success! You can now open a browser on your laptop and go to http://<raspberry-pi-ip>:8000 to see the live Digital Twin communicating with the physical robot! # Project Status & Hardware Deployment Guide

Step 3: Transfer the Code to the Pi

Since we need the raspberry-pi folder and the dashboard folder, transfer them using Secure Copy (scp) from your laptop’s terminal:

scp -r "c:\Users\santh\OneDrive - vit.ac.in\Desktop\XXX\CyberTwin-AGV\raspberry-pi" <username>@<raspberry-pi-ip>:~/
scp -r "c:\Users\santh\OneDrive - vit.ac.in\Desktop\XXX\CyberTwin-AGV\dashboard" <username>@<raspberry-pi-ip>:~/

(Alternatively, push the code to a GitHub repository and git clone it on the Pi).

Step 4: Hardware Connections

  1. Plug the flashed ESP32 into the Raspberry Pi using a USB cable.

  2. On the Pi (via SSH), check which serial port was assigned:

    ls /dev/ttyUSB*
# or
ls /dev/ttyACM*

  3. Open ~/raspberry-pi/docker-compose.yml on the Pi (using nano or vim).

  4. Update the SERIAL_PORT environment variable under the bridge service to match the port you found (e.g., /dev/ttyUSB0).

  5. Also, ensure the devices mapping in docker-compose.yml is uncommented and points to the correct port so the Docker container can access the physical USB port.

Step 5: Launch the Stack on the Pi

  1. On the Pi (via SSH), navigate to the folder:

    cd ~/raspberry-pi

  2. Build and start the edge servers:

    docker compose up -d --build

  3. Verify: Open a web browser on your laptop and go to:

    http://<raspberry-pi-ip>:8000

    You should see the Digital Twin Dashboard. Use the D-Pad to send commands—these will travel via WebSockets -> FastAPI -> MQTT -> UART Bridge -> ESP32!
